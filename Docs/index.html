01 Objectif et mode de lecture

Ce document a deux usages : comprendre les notions manipulees par le projet, et pouvoir justifier en soutenance chaque element deploye.

Inception-of-Things est un projet d'administration systeme dont le but est de decouvrir Kubernetes par la pratique, en montant progressivement quatre environnements. Le sujet impose un resultat observable a chaque etape ; ce document explique pourquoi chaque brique existe et comment elle est cablee ici.

Comment lire

  • Les sections 03 a 11 sont les notions : elles se lisent dans l'ordre, chacune s'appuyant sur la precedente.
  • La section 12 decrit ce qui est reellement implemente dans chaque partie du depot.
  • La section 13 rassemble les choix techniques et leur justification : c'est la section a relire avant la soutenance.
  • Les acronymes sont soulignes en pointilles : API, CNI, CRD. Survolez-les (ou tabulez dessus) pour afficher leur signification ; cliquez pour sauter a leur entree du lexique.
Exigence du sujet

"The whole project has to be done in a virtual machine."

"You have to put all the configuration files of your project in folders located at the root of your repository. The folders of the mandatory part will be named: p1, p2 and p3, and the bonus one: bonus."

iot.en.subject.pdf, chapitre III - General guidelines

Toute la chaine tourne donc dans une machine virtuelle d'evaluation, qui heberge elle-meme les machines virtuelles des parties 1 et 2 : c'est de la virtualisation imbriquee, et c'est le premier prerequis a verifier sur le poste de correction.

02 Vue d'ensemble

Quatre environnements, une progression : d'abord un cluster nu, puis des applications exposees, puis le deploiement automatise depuis Git, enfin la forge Git elle-meme dans le cluster.

p2 K3s, Traefik Exposition HTTP, routage par en-tete Host, replicas curl -H "Host: app1.com" 192.168.56.110

A retenir

Les parties 1 et 2 utilisent des machines virtuelles pilotees par Vagrant. Les parties 3 et bonus utilisent des conteneurs Docker : il n'y a plus de machine virtuelle, le cluster tourne dans des conteneurs sur la machine d'evaluation. C'est exactement la difference entre K3s et K3d.

03 Virtualisation et conteneurs

Deux facons d'isoler une charge de travail. Le projet utilise les deux, et il faut savoir dire laquelle sert a quoi.

Machine virtuelle

Une VM est un ordinateur complet simule par logiciel : elle possede son propre noyau, son propre systeme de fichiers, sa propre pile reseau. Le programme qui la fait tourner s'appelle un hyperviseur. VirtualBox est un hyperviseur de type 2 : il s'execute comme une application au-dessus d'un systeme d'exploitation hote, contrairement a un hyperviseur de type 1 qui s'installe directement sur le materiel.

Pour etre efficace, un hyperviseur s'appuie sur des instructions du processeur dediees a la virtualisation : VT-x chez Intel, AMD-V chez AMD. Quand la machine hote est elle-meme une machine virtuelle, il faut que l'hyperviseur du dessus expose ces instructions a son invite : c'est la virtualisation imbriquee.

Consequence pratique

Le projet est evalue dans une VM, et les parties 1 et 2 lancent des VM VirtualBox a l'interieur de celle-ci. Si la virtualisation imbriquee n'est pas activee, vagrant up echoue. Le script Tools/VM_commands.sh verifie la presence des drapeaux vmx ou svm dans /proc/cpuinfo et l'annonce.

Conteneur

Un conteneur ne simule pas de machine : il partage le noyau de l'hote et se contente d'isoler la vue qu'a un processus du systeme. Cette isolation repose sur deux mecanismes du noyau Linux :

  • namespaces : cloisonnent ce que le processus voit (arborescence de fichiers, interfaces reseau, liste des processus, utilisateurs).
  • cgroups : limitent ce que le processus consomme (CPU, memoire, entrees-sorties).

Consequence : un conteneur demarre en une fraction de seconde et pese quelques dizaines de megaoctets, la ou une VM demarre en dizaines de secondes et pese des gigaoctets. En contrepartie, l'isolation est moins forte et tous les conteneurs d'une machine partagent le meme noyau.

Image, conteneur, registre

TermeDefinitionDans le projet
Image Modele immuable en couches, contenant le systeme de fichiers et la commande de demarrage. wil42/playground:v1, nginx:alpine
Tag Etiquette de version pointant sur une image precise. Changer le tag, c'est changer la version deployee. v1 et v2 : c'est le levier de la demonstration GitOps
Conteneur Instance en cours d'execution d'une image, avec sa couche d'ecriture propre. Les processus des applications, les noeuds K3d
Registre Serveur qui stocke et distribue les images. Docker Hub (hub.docker.com/r/wil42/playground)
OCI Norme qui decrit le format des images et l'execution des conteneurs, pour qu'ils soient interoperables. Garantit que la meme image tourne sous Docker et sous containerd

Docker n'est qu'une des implementations possibles. Sous le capot, il delegue a containerd, qui delegue lui-meme a runc pour creer effectivement les namespaces et cgroups. Kubernetes n'utilise plus Docker directement : il parle a un runtime conforme a l'interface CRI. K3s embarque containerd.

04 Vagrant

Vagrant decrit une machine virtuelle dans un fichier texte versionne. C'est de l'IaC appliquee au poste de developpement : la meme commande produit la meme machine chez tout le monde.

Le reseau d'une VM Vagrant sous VirtualBox

Vagrant configure systematiquement une premiere interface en NAT : elle donne a la machine un acces sortant vers Internet et sert au SSH de gestion. Une declaration private_network ajoute une seconde interface, de type host-only : un reseau prive entre l'hote et ses machines, sur lequel on peut fixer une adresse IP stable.

Exigence du sujet

"Have a dedicated IP on the primary network interface. The IP of the first machine (Server) will be 192.168.56.110, and the IP of the second machine (ServerWorker) will be 192.168.56.111."

iot.en.subject.pdf, IV.1 - Part 1: K3s and Vagrant

VirtualBox restreint par defaut les reseaux host-only a la plage 192.168.56.0/21 : les adresses imposees par le sujet tombent dans cette plage, il n'y a donc rien a configurer. Cote invite, cette seconde interface porte un nom previsible (enp0s8 sur la plupart des distributions recentes), mais ce nom depend de la box. Le projet ne le code donc pas en dur et le deduit de l'adresse IP.

p1/scripts/install_k3s_server.shdetection d'interface
IFACE=$(ip -o -4 addr show | awk -v ip="$NODE_IP" '$4 ~ "^"ip"/" {print $2; exit}')

Cycle de vie

CommandeEffet

Connexion sans mot de passe

Les box publiques embarquent toutes la meme paire de cles, dite insecure, connue de tout le monde. Au premier demarrage, Vagrant genere une cle propre a la machine, l'installe et revoque la cle publique par defaut. C'est ce comportement qui est conserve ici : l'exigence "connect with SSH with no password" est satisfaite sans partager de secret entre les machines.

05 Kubernetes : architecture

Kubernetes est un orchestrateur : on lui decrit l'etat souhaite du systeme, il se charge de l'atteindre et de le maintenir. Tout le reste decoule de ce principe.

Declaratif et boucle de reconciliation

On ne dit pas a Kubernetes "demarre trois conteneurs" mais "je veux trois replicas de cette application". Cet etat souhaite est stocke dans la base du cluster. Des composants appeles controleurs comparent en permanence l'etat observe a l'etat souhaite et agissent pour combler l'ecart : c'est la boucle de reconciliation. Si un conteneur meurt, personne ne le relance manuellement : le controleur constate qu'il manque un replica et en cree un.

Cette propriete est ce qui rend le GitOps possible (section 10) : il suffit de brancher la source de l'etat souhaite sur un depot Git.

Les composants

ComposantRole
kube-apiserver Expose l'API REST du cluster. Point d'entree unique : kubectl, les controleurs et les kubelets ne parlent qu'a lui.
etcd / SQLite Base de donnees cle-valeur qui stocke l'integralite de l'etat du cluster. K3s utilise SQLite par defaut via kine, et non etcd.
kube-scheduler Choisit sur quel noeud placer chaque nouveau pod, selon les ressources disponibles et les contraintes.
kube-controller-manager Regroupe les boucles de controle : maintien du nombre de replicas, gestion des noeuds, des endpoints, etc.
kubelet Agent present sur chaque noeud. Recoit les pods a executer et pilote le runtime de conteneurs.
kube-proxy Programme les regles reseau du noeud pour que l'adresse d'un Service atteigne les pods correspondants.

kubectl et kubeconfig

kubectl est le client en ligne de commande. Il lit un fichier kubeconfig qui contient l'adresse de l'API server, le certificat de l'autorite du cluster et les identifiants du client. Par defaut il cherche ~/.kube/config, ou le chemin donne par la variable KUBECONFIG.

Dans p1 et p2, K3s ecrit ce fichier dans /etc/rancher/k3s/k3s.yaml avec l'adresse 127.0.0.1. Les scripts en recopient une version pour l'utilisateur vagrant en remplacant cette adresse par l'IP dediee du noeud, ce qui rend le fichier utilisable depuis l'hote.

06 Les objets Kubernetes

Tout est un objet decrit en YAML, envoye a l'API server, stocke, puis reconcilie. Voici ceux que le projet manipule.

Anatomie d'un manifest

Quatre champs sont toujours presents : apiVersion (version de l'API), kind (type d'objet), metadata (nom, namespace, labels) et spec (l'etat souhaite). Kubernetes y ajoute un champ status qu'il met a jour lui-meme.

Hierarchie de deploiement

On ne cree presque jamais un Pod directement. On declare un Deployment, qui cree un ReplicaSet, qui cree les Pods. Cet empilement permet les mises a jour progressives : lors d'un changement d'image, le Deployment cree un nouveau ReplicaSet et transfere les replicas de l'ancien vers le nouveau.

ObjetRoleUtilisation dans le projet
Namespace Cloisonnement logique des objets a l'interieur d'un meme cluster. argocd, dev, gitlab, apps
Pod Plus petite unite deployable : un ou plusieurs conteneurs partageant reseau et volumes. Une instance de wil42/playground ou de nginx
ReplicaSet Maintient un nombre donne de pods identiques. Cree implicitement par chaque Deployment
Deployment Gere les ReplicaSets et les mises a jour progressives. app1, app2 (3 replicas), app3, wil-playground
Service Adresse stable et repartition de charge vers un ensemble de pods selectionnes par label. app1-service, wil-playground-service
Ingress Regles de routage HTTP de l'exterieur vers des Services, par nom d'hote et par chemin. Routage app1.com, app2.com et defaut
IngressClass Designe quel controleur d'Ingress traite une regle donnee. traefik, declare via spec.ingressClassName
ConfigMap Donnees de configuration non sensibles, injectables en fichiers ou en variables. Les pages index.html des trois applications de p2
Secret Meme principe pour les donnees sensibles, encodees en base64 (et non chiffrees par defaut). Mot de passe initial d'Argo CD, identifiants du depot GitLab
StatefulSet Comme un Deployment, mais avec identite stable et stockage persistant par instance. argocd-application-controller, base de donnees de GitLab
DaemonSet Garantit un pod par noeud. klipper-lb, qui publie les Services de type LoadBalancer
Job Tache ponctuelle executee jusqu'a completion. Migrations de base de donnees du chart GitLab
CRD Definition d'un type d'objet ajoute a l'API par une application tierce. Application, le type apporte par Argo CD

Labels et selecteurs

Les objets ne se referencent pas par leur nom mais par des labels : des couples cle-valeur poses dans metadata.labels. Un Service declare un selector et prend en charge tous les pods qui portent ces labels. C'est le seul lien entre un Service et ses pods ; une faute de frappe dans un label produit un Service qui ne renvoie rien, sans aucune erreur.

p3/confs/service.yamlextrait
spec:
  selector:
    app: wil-playground   # doit correspondre au label des pods du Deployment
  ports:
    - port: 8888          # port du Service
      targetPort: 8888    # port ecoute dans le conteneur

Les types de Service

TypePorteeRemarque
ClusterIPInterne au cluster uniquement. Type par defaut, utilise partout dans le projet
NodePortOuvre le meme port sur tous les noeuds. Plage 30000-32767, non utilise ici
LoadBalancerDemande une adresse externe a l'infrastructure. Fourni par klipper-lb dans K3s ; occupe les ports 80 et 443 des noeuds pour Traefik

07 Le reseau Kubernetes

Le modele reseau de Kubernetes tient en une phrase : chaque pod recoit une adresse IP unique et tous les pods peuvent se joindre directement, sans traduction d'adresse.

Le CNI et flannel

Kubernetes ne sait pas faire de reseau : il delegue a un greffon conforme a l'interface CNI. K3s embarque flannel, qui utilise par defaut l'encapsulation VXLAN : les paquets destines a un pod situe sur un autre noeud sont enveloppes dans des paquets UDP normaux, transportes par le reseau physique, puis desencapsules a l'arrivee.

Il faut donc dire a flannel sur quelle interface parler. Sur une VM Vagrant il y a au moins deux interfaces : celle de NAT, identique sur toutes les machines, et celle du reseau prive. Si flannel choisit la mauvaise, les deux noeuds croient partager la meme adresse et le trafic inter-noeuds ne fonctionne pas. D'ou le drapeau --flannel-iface, alimente ici par l'interface deduite de l'IP du noeud.

Les plages d'adresses

PlageValeur par defaut dans K3sContenu
Pod CIDR10.42.0.0/16Adresses attribuees aux pods
Service CIDR10.43.0.0/16Adresses virtuelles des Services
DNS du cluster10.43.0.10Service CoreDNS
Reseau host-only192.168.56.0/24Reseau prive VirtualBox impose par le sujet

La resolution de noms

CoreDNS donne a chaque Service un nom stable de la forme <service>.<namespace>.svc.cluster.local. Un pod du namespace argocd peut ainsi joindre GitLab dans le namespace gitlab sans connaitre aucune adresse IP :

bonus/confs/application.yamlrepoURL interne
repoURL: http://gitlab-webservice-default.gitlab.svc.cluster.local:8181/root/iot-app.git

C'est ce qui rend le bonus reellement autonome : Argo CD ne sort jamais du cluster pour recuperer ses manifests.

Service ou Ingress ?

Un Service travaille au niveau 4 (TCP) : il ne connait que des adresses et des ports. Un Ingress travaille au niveau 7 (HTTP) : il lit l'en-tete Host et le chemin de la requete pour choisir le Service de destination. C'est exactement ce que demande la partie 2 : une seule adresse IP, trois applications, differenciees par le nom d'hote.

Pourquoi la regle par defaut fonctionne

Traefik attribue a chaque regle une priorite egale a la longueur de son expression. La regle Host(`app1.com`) && PathPrefix(`/`) est plus longue que PathPrefix(`/`), elle est donc evaluee en premier. La regle sans hote ne capte que ce qui n'a matche aucune autre : elle joue naturellement le role de defaut demande par le sujet pour app3.

08 K3s

K3s est une distribution Kubernetes certifiee, condensee dans un binaire unique, concue pour les environnements contraints. C'est le meme Kubernetes, avec moins de pieces a assembler.

Ce qui change par rapport a Kubernetes standard

  • Un seul binaire embarque l'API server, le scheduler, le controller-manager, le kubelet, containerd et flannel.
  • Le stockage par defaut n'est pas etcd mais SQLite, via une couche de traduction appelee kine. etcd n'apparait que dans la configuration en HA a plusieurs serveurs.
  • Les greffons cloud et les fonctions historiques ou experimentales sont retires.
  • Des composants utiles sont pre-installes et se deploient automatiquement au demarrage.

Les composants installes d'office

ComposantRoleConsequence dans le projet
TraefikControleur d'Ingress. Aucune installation a faire en p2 et p3 : l'Ingress fonctionne d'emblee
CoreDNSServeur DNS interne. Resolution des noms de Services
klipper-lbImplementation minimale des Services LoadBalancer. Publie Traefik sur les ports 80 et 443 des noeuds
local-path-provisionerStockage persistant sur le disque local du noeud. Utilise par les composants de GitLab dans le bonus
metrics-serverCollecte CPU et memoire. Alimente kubectl top

Server et agent

Un noeud server execute le plan de controle et accepte aussi des charges de travail. Un noeud agent n'execute que le kubelet et le runtime : il rejoint un server existant et se contente de faire tourner des pods. C'est exactement la repartition demandee par le sujet pour la partie 1.

Exigence du sujet

"You must install K3s on both machines: in the first one (Server), it will be installed in controller mode. In the second one (ServerWorker), in agent mode."

iot.en.subject.pdf, IV.1 - Part 1: K3s and Vagrant

Le node-token

Pour rejoindre un cluster, un agent doit prouver son identite avec un secret partage : le node-token, genere par le server et depose dans /var/lib/rancher/k3s/server/node-token. L'agent le fournit via la variable K3S_TOKEN, avec l'adresse du server dans K3S_URL.

Toute la difficulte du provisionnement automatise tient a la transmission de ce secret d'une machine a l'autre. Le projet le fait passer par le dossier synchronise, deja monte dans les deux machines (voir section 13).

09 K3d

K3d lance K3s dans des conteneurs Docker. Un cluster complet demarre en quelques secondes, sans machine virtuelle.

Exigence du sujet

"You now master a minimalist version of K3s! Time to set up everything you have just learnt (and much more!) but without Vagrant this time. To begin, install K3d on your virtual machine."

"First of all, you must understand the difference between K3s and K3d."

iot.en.subject.pdf, IV.3 - Part 3: K3d and Argo CD

La difference, en une phrase

K3s est une distribution Kubernetes que l'on installe sur une machine ; K3d est un outil qui cree des clusters K3s dans des conteneurs Docker. K3d n'est pas une autre version de Kubernetes : c'est un emballage de K3s pour le poste de developpement.

K3s (p1, p2)K3d (p3, bonus)
Un noeud estune machine virtuelleun conteneur Docker
PrerequisVagrant + VirtualBoxDocker
Temps de creationplusieurs minutesquelques secondes
Acces reseauIP dediee sur le reseau host-onlypublication de ports Docker vers localhost
Isolationnoyau separenoyau partage avec l'hote

Ce que K3d cree

  • k3d-iot-cluster-server-0 : le noeud server.
  • k3d-iot-cluster-agent-0 et -agent-1 : les noeuds agents.
  • k3d-iot-cluster-serverlb : un conteneur proxy place devant les noeuds, qui recoit les ports publies vers l'hote.
  • un reseau Docker dedie reliant le tout.

La publication de ports

C'est le point le plus souvent mal compris. La syntaxe --port "<hote>:<interne>@loadbalancer" publie un port de la machine hote sur le conteneur serverlb, lequel relaie vers le meme numero de port sur les noeuds. Il faut donc que quelque chose ecoute reellement sur ce port du noeud.

Piege classique

--port "8888:8888@loadbalancer" ne fonctionne pas ici : rien n'ecoute sur le port 8888 des noeuds. Le Service de l'application est de type ClusterIP, donc interne, et la plage des NodePort commence de toute facon a 30000. Le port publie est bien ouvert sur l'hote, mais il ne mene nulle part.

La formulation correcte est --port "8888:80@loadbalancer" : le port 8888 de l'hote est branche sur le port 80 des noeuds, ou Traefik ecoute deja. L'Ingress prend alors le relais et route vers le Service sur son port 8888.

10 GitOps et Argo CD

Le GitOps pousse la logique declarative de Kubernetes jusqu'au bout : l'etat souhaite n'est plus dans les mains d'un operateur, il est dans un depot Git, et un agent se charge en permanence de faire converger le cluster vers ce contenu.

Les quatre principes

  1. Declaratif : tout le systeme est decrit par des fichiers, pas par des commandes.
  2. Versionne : ces fichiers vivent dans Git, avec historique, revue et retour arriere.
  3. Applique automatiquement : un agent lit le depot et applique les changements, sans intervention.
  4. Reconcilie en continu : l'agent surveille l'ecart entre le depot et le cluster, et le corrige.

Modele pull contre modele push

Dans une chaine CI/CD classique, le serveur d'integration pousse vers le cluster : il faut lui confier des identifiants d'administration du cluster. En GitOps, l'agent vit dans le cluster et tire depuis le depot. Le cluster n'expose rien vers l'exterieur et aucun secret d'acces ne sort. C'est plus sur, et cela permet la reconciliation permanente.

La derive et l'auto-reparation

On appelle drift l'ecart entre l'etat decrit dans Git et l'etat reel du cluster : quelqu'un modifie une ressource a la main, un objet est supprime par erreur. Deux options de synchronisation traitent ce cas :

  • selfHeal: true : toute modification faite directement sur le cluster est annulee et remplacee par le contenu du depot.
  • prune: true : une ressource supprimee du depot est supprimee du cluster. Sans cette option, elle survivrait indefiniment.

Les composants d'Argo CD

ComposantRole
argocd-serverSert l'API et l'interface web. Ecoute en HTTPS sur le port 443 du Service.
argocd-repo-serverClone les depots Git et produit les manifests finaux (YAML brut, Helm ou Kustomize).
argocd-application-controllerCoeur du systeme : compare l'etat souhaite a l'etat reel et applique les differences. Deploye en StatefulSet.
argocd-redisCache des manifests et des etats calcules.
argocd-dex-serverDelegation d'authentification vers un fournisseur externe. Non utilise ici.

L'objet Application

Argo CD ajoute a l'API Kubernetes un type d'objet via une CRD : Application. Cet objet est la seule chose que le projet applique a la main ; tout le reste en decoule.

p3/confs/application.yamlannote
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: wil-playground-app
  namespace: argocd              # l'Application vit dans le namespace d'Argo CD
spec:
  project: default
  source:
    repoURL: https://github.com/BekxFR/trobert-iot-argocd-app.git
    targetRevision: HEAD         # branche par defaut du depot
    path: .                      # repertoire des manifests dans le depot
  destination:
    server: https://kubernetes.default.svc   # le cluster local
    namespace: dev               # ou deployer
  syncPolicy:
    automated:
      prune: true                # supprime ce qui disparait du depot
      selfHeal: true             # annule les modifications manuelles
    syncOptions:
      - CreateNamespace=true     # cree le namespace s'il manque
Point de vigilance

Le depot Git fait foi. Les fichiers de p3/confs/ sont une copie de reference pour la lecture et la mise en place : ce sont les manifests du depot GitHub qu'Argo CD applique reellement. Toute modification locale doit y etre repercutee, sinon les deux divergent silencieusement.

Le cycle de synchronisation

Par defaut, Argo CD interroge le depot toutes les trois minutes. En soutenance, il ne faut pas attendre : le bouton Refresh de l'interface ou la commande argocd app sync wil-playground-app declenche la synchronisation immediatement.

Acces a l'interface

Le Service argocd-server reste en ClusterIP. Il s'atteint par un tunnel local :

# puis https://localhost:8080 (certificat auto-signe : avertissement normal)

11 Helm et GitLab

La partie bonus remplace GitHub par une forge Git installee dans le cluster. Deux notions supplementaires : Helm pour installer un logiciel complexe, et l'architecture interne de GitLab.

Helm

GitLab represente plusieurs dizaines d'objets Kubernetes. Les ecrire a la main serait ingerable. Helm est le gestionnaire de paquets de Kubernetes : il distribue des charts, c'est-a-dire des modeles de manifests parametrables.

TermeDefinition

Le fichier bonus/confs/gitlab-values.yaml desactive tout ce qui n'est pas necessaire (registre d'images, Prometheus, cert-manager, runner, stockage objet, Pages) afin de tenir dans les ressources d'une machine d'evaluation.

Automatiser GitLab

Le script bonus/scripts/configure_gitlab.sh enchaine, sans intervention manuelle :

  1. Lecture du mot de passe root dans le Secret cree par le chart.
  2. Ouverture d'un tunnel vers le service web, puis attente que l'API reponde.
  3. Creation d'un PAT via gitlab-rails runner dans le pod toolbox, avec repli sur un jeton OAuth obtenu par mot de passe.
  4. Creation du projet iot-app en visibilite publique, par l'API v4.
  5. Initialisation d'un depot local, copie des manifests, puis git push.
  6. Declaration du depot aupres d'Argo CD sous forme de Secret portant le label argocd.argoproj.io/secret-type: repository.
Pourquoi HTTP et insecure

Argo CD joint GitLab par son nom de Service interne, en clair sur le port 8181. Le trafic ne quitte jamais le reseau du cluster, et aucune autorite de certification n'est deployee : le champ insecure: "true" du Secret indique simplement a Argo CD de ne pas exiger de verification TLS. Dans un contexte de production, on installerait un certificat plutot que de desactiver la verification.

13 Choix techniques et justifications

Chaque ligne de ce tableau est une question probable en soutenance. La reponse tient en une phrase, la justification en trois.

Pourquoi la box bento/ubuntu-26.04

Le sujet impose la derniere version stable de la distribution. Les images officielles Debian ne sont plus publiees que pour libvirt, donc inutilisables avec VirtualBox. Canonical ne publie plus de box au-dela de Ubuntu 22.04. Le catalogue bento, maintenu et couvrant VirtualBox en amd64, propose Ubuntu 26.04 LTS : c'est la seule combinaison qui satisfait a la fois l'exigence de fraicheur et le provider impose par le reste du projet.

Pourquoi detecter l'interface reseau

Le nom de la seconde interface (enp0s8, eth1, ...) depend de la distribution et de sa version. Le coder en dur signifie que tout changement de box casse silencieusement flannel : le cluster se forme, mais le trafic inter-noeuds ne passe plus. La deduction depuis l'IP supprime cette classe entiere de panne.

Pourquoi le token passe par le dossier synchronise

L'agent a besoin d'un secret detenu par le server. Trois solutions existaient :

SolutionInconvenient
Copier la cle privee insecure de Vagrant dans le worker et faire un SSH entre machines Impose insert_key = false, donc une cle publiquement connue sur les deux machines ; depend d'un chemin de l'hote qui peut changer selon la version de Vagrant.
Ecrire un token fixe dans le depot Secret en dur, versionne.
Publier le token dans le dossier synchronise Aucun. Le dossier est deja monte dans les deux machines, le fichier est ignore par git, et Vagrant peut conserver son insertion de cle par machine.

Le sujet insiste sur des "modern practices" pour le Vagrantfile : conserver la generation de cle par machine est precisement cela.

Pourquoi ingressClassName plutot que l'annotation

L'annotation kubernetes.io/ingress.class est depreciee depuis Kubernetes 1.18 et n'est plus lue par Traefik v3, embarque dans les versions recentes de K3s. Elle a un effet de bord peu connu : sa presence empeche l'API server d'affecter automatiquement l'IngressClass par defaut. Le champ spec.ingressClassName est la forme normalisee et explicite.

Pourquoi le port 8888 est branche sur le port 80

Voir section 09 : publier 8888:8888 ouvre un port qui ne mene nulle part, puisque rien n'ecoute sur le port 8888 des noeuds. Brancher le port 8888 de l'hote sur le port 80 des noeuds place Traefik dans le chemin, et l'Ingress route vers le Service. La commande curl http://localhost:8888 du sujet fonctionne alors sans tunnel.

Pourquoi argocd-server reste en ClusterIP

Passer ce Service en LoadBalancer semble pratique, mais dans K3s le type LoadBalancer est realise par klipper-lb, qui reserve les ports concernes sur les noeuds. Traefik occupe deja 80 et 443 : le second service reste indefiniment en attente d'adresse. Le tunnel kubectl port-forward est la methode standard, immediate et sans conflit.

Pourquoi rollout status plutot que wait

kubectl wait --for=condition=ready pod -l ... echoue immediatement, avec le message no matching resources found, si aucun pod ne correspond encore au selecteur. Juste apres un apply, c'est le cas le plus frequent. kubectl rollout status porte sur le Deployment, qui existe des l'application du manifest. Pour les ressources creees par Argo CD, une boucle attend d'abord l'apparition du pod, puis kubectl wait attend sa disponibilite.

Pourquoi les scripts sont en set -e avec des attentes explicites

Un sleep 30 est un pari : trop court il masque une erreur, trop long il fait perdre du temps. Les scripts attendent une condition observable (l'API repond, le service est actif, le pod existe) avec une borne maximale et un message de diagnostic. Un echec devient visible immediatement, au lieu de se manifester trois etapes plus loin.

15 Depannage

Les pannes reellement rencontrees sur ce projet, leur cause et leur correction.

SymptomeCauseCorrection
vagrant up echoue : VT-x indisponible Virtualisation imbriquee desactivee sur la VM d'evaluation. L'activer dans l'hyperviseur hote. Tools/VM_commands.sh signale le probleme des le depart.
Erreur de permission sur /dev/vboxdrv L'utilisateur n'appartient pas au groupe vboxusers, ou le module n'est pas charge. sudo usermod -aG vboxusers $USER puis reconnexion ; verifier lsmod | grep vbox.
Disque plein pendant vagrant up Les box et disques sont stockes sous /tmp, monte en tmpfs (donc en RAM) sur certaines distributions. make VM_STORAGE=$HOME/iot-vms p1
"A VM with the name chillionS already exists" Une machine du meme nom subsiste d'une execution precedente. make fclean, ou VBoxManage unregistervm chillionS --delete.
Le noeud agent reste absent de kubectl get nodes Token non recupere, ou flannel sur la mauvaise interface. Verifier p1/confs/node-token, puis journalctl -u k3s-agent dans la machine.
docker: permission denied L'utilisateur vient d'etre ajoute au groupe docker mais la session n'a pas ete rouverte. newgrp docker ou reconnexion.
curl localhost:8888 renvoie 404 L'Ingress existe mais aucune regle ne correspond, ou le Service ne selectionne aucun pod. kubectl get ingress -n dev puis kubectl get endpoints -n dev : un endpoint vide signale un selecteur errone.
Argo CD affiche OutOfSync sans jamais deployer Depot inaccessible, chemin errone, ou branche inexistante. kubectl describe application wil-playground-app -n argocd : le message d'erreur figure dans les conditions.
Un Service LoadBalancer reste en Pending Le port demande est deja occupe sur les noeuds par un autre Service (Traefik). Utiliser kubectl port-forward plutot que de changer le type du Service.
Les pods GitLab restent en Pending Ressources insuffisantes sur la machine d'evaluation. Liberer de la memoire, ne pas faire tourner p1 ou p2 en meme temps, verifier avec kubectl describe pod.

Reflexe de diagnostic

  1. kubectl get pods -A : quel objet n'est pas dans l'etat attendu ?
  2. kubectl describe sur cet objet : la section Events donne presque toujours la cause.
  3. kubectl logs si le conteneur demarre puis s'arrete.
  4. Pour une VM, journalctl -u k3s ou journalctl -u k3s-agent.
